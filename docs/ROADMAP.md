# 路线图

> 本文回答一个问题：**开工前定的规划，在查清现状之后要改哪几处。**

---

## 1. 规划修订：四处必须改

### 修订 1：数据源路线从"补 Cookie"升级为"换基站 + 建设备身份"

- **原计划**：以 `fanqie.koplugin` 为骨架，补上官方账号登录/书架/进度同步。
- **查清的事实**：问题不在"有没有登录"，而在**基站选错了**。Web 端
  `fanqienovel.com` 即使带着合法 `sessionid`，正文也拿不到；移动端 API 需要
  `install_id` + `device_id` 这套**已注册设备**的身份，而现有代码完全没有这一环。
- **改为**：新增 `fanqie/device.lua`（设备注册 + 持久化）与 `fanqie/mobile.lua`
  （移动端请求头与响应解析），默认数据源切到移动端，Web 端作为可回退项。
  详见 `docs/API.md`。

### 修订 2：把"一章一文档"列为必须先修的架构债，且优先级高于数据源

- **原计划**：先让它能抓到正文，体验问题后面再说。
- **查清的事实**：现在的阅读链路是"每章存一个 `.html`，每章调一次
  `ReaderUI:showReader()`"，于是每翻一章都换一个 KOReader 文档——分页、进度、
  目录、历史全部重置，为此欠下了五个猴补丁。详见 `docs/ARCHITECTURE.md`。
- **改为**：**先做整书 EPUB，再接数据源。** 理由是顺序性的：进度同步要同步的是
  "整本书读到第几章第几页"；在一章一文档的架构下，本插件眼里的"进度"本身就
  是碎的，此时去对接官方进度接口只会把错误模型写死进代码。

### 修订 3："参考实现"不可读，改为探针先行

- **原计划**：参照 `Fanqie-novel-Downloader` 的官方账号登录与书架同步实现。
- **查清的事实**：该仓库公开内容只有文档/CI/脚本，**没有业务源码**。
  可用的一手证据只有两处：(a) 本机已安装的桌面版 `fanqie-desktop.exe` 里
  扫出的接口路径；(b) 本机客户端留下的缓存文件里的真实字段结构。
- **改为**：把"照着参考实现抄"换成**探针先行**的流程：
  先写只读探针（`tools/`）把真实响应落盘看清楚，再写解析与用例。
  未经探针确认的接口细节一律标注为"待验证"，不写进正式代码。

### 修订 4：测试基座从"锦上添花"变成"动工前置条件"

- **原计划**：测试放到最后，先做出能跑的东西。
- **查清的事实**：KOReader 官方**不支持 Windows**（模拟器仅 Linux/macOS），
  本机连"打开看一眼"都做不到。在没有任何可运行反馈的情况下改一个
  3200 行的 `main.lua`，等于盲写。
- **改为**：先建测试基座（**已完成**），再用它给纯逻辑模块上用例，最后才动
  `main.lua` 与 `patches/`。详见 `docs/TESTING.md`。

## 3. 明确不做的事

- **不做内容下载站**：仓库不分发小说文本，也不提供批量抓取全站的服务。
- **不做云端同步**：进度只走官方账号接口，不引入任何第三方服务器。
- **不改 KOReader 核心**：新增的猴补丁要越少越好；M3 的目标是**删补丁**而不是加。
- **不承诺接口永久可用**：移动端接口是逆向来的，README 里要如实写明这一点，
  不能给用户"装上就永远能用"的错觉。

## 4. 当前风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 正文接口参数未验证 | M2 可能返工 | 探针先行，先落盘响应再写解析 |

| **CI 工作流尚未真实运行过** | 首次推送到 GitHub 时可能才暴露问题 | L1 与打包在本机已实测通过（含 `--strict` 与 zip 自检）；CI 里的 `lua-native` 依赖（lua-filesystem / luacheck 的 luarocks 安装）**只能等第一次 push 才算验证**，届时按报错修 |
| 上游代码更新 | 与本仓库改动冲突 | 上游源码放在 `refs/`（gitignore），本仓库以 `src/` 为唯一事实源 |
